# 做完这个项目，你应该能解释和独立完成什么？

这个项目适合用你的数学基础补足可复现数值实验、PyTorch 和 agent 工具调用经验。目标不是背会框架名称，而是能独立说明：数据从哪里来，结果为何可信，哪些差异来自反馈，以及结论不能推广到哪里。

建议按 **四周、总计约 40–60 小时** 安排。时间是学习与整理报告的估计，不是已测得的运行耗时；Python 环境、调试经验和 Codex 可用性会影响进度。先读 [实验方案](EXPERIMENT_PLAN.md)，再按下面顺序做，每周留下可检查的产物。

## 第一周：从金融公式到可信数据（约 8–12 小时）

**要掌握：** 欧式看涨期权的支付函数；现价、行权价、期限、波动率的含义；Black–Scholes 的模型假设；向量化计算、数值边界处理、随机种子与数据划分。

这里的“正确答案”是**在指定理论模型下的价格**，不是预测未来实际成交价。你需要能解释为何使用同一条报价反推出的隐含波动率再重建价格，不能证明预测能力；也要理解合成实验使用随机划分，而历史时间序列通常需要按时间划分。

实践顺序：

1. 阅读 `pricing.py`，手算一个到期支付 `max(S-K,0)`，再比较程序结果。
2. 在固定其他参数时改变 `S`、`T`、`sigma`，描述价格变化；明确你采用的无分红、正利率假设。
3. 阅读 `data.py`，画出训练与压力诊断数据的参数分布。解释为什么后者强调短期限而前者不强调。
4. 运行外部参考与边界测试。故意修改一个公式符号，确认测试确实会发现错误，然后恢复。
5. 自己解释为什么 QuantLib 的 22 条参考值只用于公式检查，而不能承担神经网络的训练数据集。

**本周产物：** 一页数据说明、两张参数/价格图，以及对一个参考样例的手工核对。

**可能的发现：** 价格的量级会随参数改变；直接比较相对误差在接近零的期权价格处可能产生误导。由此理解本实验选择绝对误差并用 `K` 归一化的原因。

## 第二周：训练网络，检查导数（约 10–15 小时）

**要掌握：** PyTorch 张量、前向传播、损失、反向传播、Adam、输入缩放、验证选模、提前停止、checkpoint，以及 `eval` 与冻结模型的含义。

实践顺序：

1. 阅读 `model.py`，标出从物理参数到网络输入、再到 `C/K` 的完整映射。
2. 在单独的学习目录中训练一个网络，画训练和验证曲线；正式研究的配置不因此改变。
3. 解释训练集为何更新权重，验证集为何选择 checkpoint，测试集为何最后才用于报告。
4. 对比均方误差、平均绝对误差和最大误差。找一个“平均误差较小但局部误差较大”的例子。
5. 计算网络 delta，并与解析 delta、有限差分对照，确认链式法则和单位正确。

如果网络学习 `C/K=f(m,T,sigma)` 且 `m=S/K`，则 `delta=df/dm`。但若代码内部把 `m` 变换到 `[-1,1]`，求导时必须继续乘归一化变换的导数。让自动微分跟踪物理输入可以处理这条链。

**本周产物：** 训练曲线、保存的模型、独立误差表、至少一个价格与 delta 的对照例子。

**可能的发现：** 小的函数值误差不保证小的导数误差。你可以从数学上构造一个振幅小但变化快的扰动解释这一点，再检查训练出的网络是否也出现类似现象。若未出现，应如实报告。

## 第三周：设计公平的搜索比较（约 10–15 小时）

**要掌握：** 随机采样、Sobol 低差异采样、差分进化、压力测试、相同预算、开发与最终评估分离、配对实验与重复实验的层级。

实践顺序：

1. 在二维投影上比较随机点和 Sobol 点，说明均匀覆盖不等于最优的错误搜索。
2. 用一句话描述 DE：“保持一组候选点，利用已有点构造新点，按测得的目标值更新候选。”然后读目标函数如何取负号以寻找最大误差。
3. 在旧开发网络上查看 DE 种群大小的选择过程，理解为什么过大的种群在固定预算下会减少迭代次数。
4. 审查七个固定金融压力区域，写出每个区域对应的金融或近似难点。
5. 运行新的数值比较，核对所有初始化与后续评估均计入 1,024 点预算。
6. 画搜索曲线，分别讨论“极端误差”和“失败参数覆盖”。不要把两者混成一个事后挑选的结论。

**本周产物：** 四种数值方法的完整比较、逐模型结果、一个描述取舍的图。

**可能的发现：** 金融压力规则可能很强；数值优化可能在低维空间里既快又有效；随机覆盖可能发现较多不同区域，而自适应方法集中在少数极端位置。这些是待验证的可能性，不是预设结论。

## 第四周：运行 agent 对照并写成研究结论（约 12–18 小时）

**要掌握：** 提示词与工具接口、JSON schema、输入校验、实验记录、反馈消融、调用成本及失败恢复规则。

实践顺序：

1. 先在学习会话中手写一个合法区域 JSON，提交给工具，读懂返回的实际测量结果。
2. 阅读 Codex 桥接脚本：区分 LLM 的提议与 Python 的执行；明确哪些输出会给 agent，哪些应保持隐藏。
3. 在已登录的本机 Codex CLI 上选择一个实际可用的明确模型 ID。核对固定配置，再运行两个 LLM 条件。
4. 检查无反馈组的输入，确认其中没有后续误差、累计最好点或其他泄漏。检查反馈组也看不到竞争方法与独立诊断结果。
5. 抽查原始模型输出、解析后的提议和逐点评分是否能对应。失败调用不能删除或伪造。
6. 按相同网络和搜索种子比较反馈/无反馈差异，再与金融规则和 DE 比较，记录耗时与实际可观测的调用信息。
7. 写一页结果说明和一段 3–5 分钟演示，包含一个方法失败或无优势的例子。

**本周产物：** 可审计的 LLM 日志、配对结果表、最终报告和简短演示。

完整矩阵计划有 126 次 LLM 决策。当前交付环境不具备可用的已登录 Codex CLI；在真实运行完成前，只能说“数值实验已完成、LLM 实验待执行”，不能把此前的手动 pilot 填入正式表格。

## 实验结束后，可能得到哪些不同发现？

| 观察到的结果 | 可以支持的解释 | 还不能说明什么 |
|---|---|---|
| 反馈组稳定优于同模型无反馈组 | 在本任务与固定协议下，新数值结果有助于选择测试区域 | LLM 已经能适应市场或盈利 |
| 两个 LLM 组接近，金融压力规则也很强 | 既有金融知识或固定压力点可能解释主要效果 | 所有 agent 任务中反馈都没用 |
| 反馈组优于无反馈组，但 DE 更好、更快 | 反馈有作用，但常规数值优化更适合当前低维任务 | LLM 在其他更复杂工具任务中也没有价值 |
| 反馈组找到更大极端误差，但覆盖更少网格 | 搜索集中于少数薄弱区域；指标之间存在取舍 | 覆盖少必然更差，或极端误差大必然更好 |
| 平均价格误差较小，但 delta 误差明显 | 只验证函数值可能漏掉敏感度风险 | 已证明实际对冲会损失多少 |
| 结果只在一个网络明显 | 效果依赖训练实例，需要谨慎解释 | 已得到可推广的模型间优势 |
| 调用频繁无效或耗时很高 | Agent 的工程可靠性/成本是实际限制 | 仅看成功案例就足以评价整体表现 |

若主要结果是零提升，先检查协议和实现是否正确，再接受结论。不要不断修改提示词直到在正式测试网络上“获胜”；这样的网络已经变成开发集，下一轮需要新实例。

## 对 quant 与 model risk 求职有什么具体帮助？

完成并真正理解代码后，你应能用项目回答这些面试问题：

- **数据泄漏：** 为什么验证集、最终诊断集、搜索反馈与开发网络必须分开？
- **模型风险：** 理论模型误差、神经近似误差、数值实现错误有什么区别？本项目实际测的是哪一种？
- **Greeks：** 为什么 delta 与价格同时检查？归一化后如何正确求导？
- **实验设计：** 为什么要同模型、同种子配对？为什么九组设置不等于九个独立网络？
- **优化：** Sobol 与 DE 分别适合什么？为什么等查询预算仍不等成本？
- **Agent 工程：** 模型输出错误 JSON 时怎么办？怎样保证评分来自工具而不是模型自述？
- **结论边界：** 有哪些结果足以说明反馈有用，又有哪些不能推出交易收益？

展示时先讲清楚研究问题、对照组和一项实际发现，再讲模型或 agent 框架。你的数学优势可以体现为误差与导数的解释、变量变换、约束检查和对结论适用范围的判断；代码与日志则证明你能把这些判断落实为可复现的实验。

这会形成一个可讨论的量化研究/模型验证作品，但不会单独覆盖求职所需的概率、统计、算法、SQL、时间序列和交易知识，也不保证某类岗位录用。首版完成后，优先补齐真实 LLM 对照与清楚的报告，再决定是否需要更复杂的定价模型。
